# 04 最小数据契约 v0.1（2026-10-31，待 Codex 审）

> 用途：让网站能表达「多阶段赛事、临时组队、BO 多局、历史名单、构想中的未来赛事」，同时不把构想写成已定规则。
> 原则：**单一数据源 → 生成静态页**；页面不手写数据；契约不通过不进样板实现。
> 状态：v0.1 草案；Codex 审核后按 CHANGES 修订，再进入 M1 样板。

## 1. 实体与关系

```
SourceRef（来源）
   ↑ 被所有公开数字引用
Person（人物，稳定 ID）── RosterEntry（参赛名单，绑定 Event[, Phase]）
Team（队伍，名称历史）───┘
Event（赛事/活动）── Phase（阶段：季前/常规/季后赛/单日赛/资格赛）
   └── Match（对阵/场次，BO 几）── Game（对阵内单局）── PlayerGameStat（单局选手数据）
                                          └── TimelineEvent（击杀/推塔/资源事件）
Announcement（公告，可挂 Event 或全站）
Ruleset（规则集 + 版本，历史与未来赏金赛分开）
```

关键点：
- **Person 与赛事、昵称解耦**；同人跨位置/跨赛事通过 RosterEntry 与 alias 关联，不复制人物。
- **RosterEntry 必须绑定具体 Event（必要时 Phase）**；新队伍不能覆盖历史名单。
- **Event 的「活动类别 / 阶段 / 组队方式 / 淘汰方式 / 规则集」是五个独立字段**，不合成一个「模式」枚举。
- **Match 与 Game 分开**：一场 BO 对阵含多局；单局战报、时间线、统计都挂 Game。

## 2. 两个独立状态维度（不共用一个字段）

### 2.1 `publish_status`（方案是否获准发布）

| 值 | 含义 | 页面展示 |
|---|---|---|
| `concept` | 构想，尚非已公布规则 | 「筹备方案，尚未公布」；不得出现日期/倒计时/报名中/奖金 |
| `pending` | 方案待确认 | 「待确认」 |
| `announced` | 已公布 | 可展示已确认信息与来源 |
| `archived` | 历史归档 | 「历史赛事/历史方案」 |

### 2.2 `progress_status`（赛事进行到哪）

| 值 | 含义 |
|---|---|
| `tbd` | 未确定 |
| `scheduled` | 已排期（须有 `schedule_status=confirmed` + 来源） |
| `live` | 进行中 |
| `completed` | 已结束 |
| `cancelled` | 已取消 |

**校验**：`concept` 事件只能是 `tbd`；`scheduled` 必须有确认日期与来源；「待讨论」和「已结束」绝不能写进同一个状态字段。

## 3. 最小字段表

### 3.1 Person（人物）

| 字段 | 类型 | 必填 | 说明 |
|---|---|---|---|
| `person_id` | string | 是 | 稳定 ID（`p_0001`），不随昵称/赛事变化 |
| `display_name` | string | 是 | 当前公开显示的游戏昵称 |
| `nickname_history` | array | 否 | `{name, from, source_ref_id}` |
| `identity_status` | enum | 是 | `confirmed` / `candidate` / `pending` |
| `merged_into` | string/null | 否 | 合并目标 person_id；合并需 `confirmed_by/confirmed_at/evidence_ref_id` |
| `privacy_flags` | array | 否 | `hide_profile` / `delete_requested` 等 |

### 3.2 Team（队伍）

| 字段 | 类型 | 必填 | 说明 |
|---|---|---|---|
| `team_id` | string | 是 | 稳定 ID |
| `name` | string | 是 | 当前显示队名 |
| `name_history` | array | 否 | 改名记录，不覆盖旧名 |
| `team_status` | enum | 否 | `confirmed` / `candidate` |

### 3.3 Event（赛事/活动）

| 字段 | 类型 | 必填 | 说明 |
|---|---|---|---|
| `event_id` | string | 是 | 稳定 ID |
| `title` | string | 是 | 如「赏金赛第一把」「2026 长周期赛事（筹备）」 |
| `category` | enum | 是 | `formal_league` / `bounty_event` / `ranked_night` / `other`（活动类别） |
| `publish_status` | enum | 是 | 见 2.1 |
| `progress_status` | enum | 是 | 见 2.2 |
| `ruleset_id` | string | 是 | 规则集版本；历史与未来赏金赛不同 ID |
| `team_formation` | enum | 是 | `fixed` / `auction` / `random_matching` / `invited` / `unknown` |
| `elimination_format` | enum | 是 | `single_elim` / `double_elim` / `round_robin` / `bo_series` / `unknown` |
| `schedule_status` | enum | 是 | `confirmed` / `tbd`（未确认只能 tbd） |
| `start_at` / `end_at` | string/null | 否 | ISO 时间；`schedule_status=tbd` 时必须为 null；显示「赛程待公布」 |
| `summary` | string | 否 | 一句话说明；受 publish_status 约束 |
| `source_ref_id` | string | 是 | 依据来源 |

### 3.4 Phase（阶段）

| 字段 | 类型 | 必填 | 说明 |
|---|---|---|---|
| `phase_id` | string | 是 | 稳定 ID |
| `event_id` | string | 是 | 所属赛事 |
| `kind` | enum | 是 | `preseason` / `regular` / `playoffs` / `one_day` / `qualifier` / `other` |
| `order` | int | 是 | 展示顺序 |
| `window_status` | enum | 是 | `confirmed` / `tbd` |
| `format_note` | string | 否 | 如「单败，一天内完成」；与规则集分开记录 |

### 3.5 RosterEntry（参赛名单）

| 字段 | 类型 | 必填 | 说明 |
|---|---|---|---|
| `roster_id` | string | 是 | 稳定 ID |
| `event_id` | string | 是 | 必须绑定赛事 |
| `phase_id` | string/null | 否 | 阶段级名单时填 |
| `team_id` | string | 是 | 所属队伍 |
| `person_id` | string | 是 | 人物 |
| `role` | string/null | 否 | 游戏内分路（可空） |
| `role_status` | enum | 是 | `confirmed` / `candidate` / `unknown` |
| `joined_at` | string/null | 否 | 入队/参赛时间 |
| `snapshot_version` | string | 是 | 名单快照版本；历史名单只追加不覆盖 |
| `evidence_ref_id` | string | 是 | 名单依据（截图/报名表/公告） |

### 3.6 Match（对阵/场次）

| 字段 | 类型 | 必填 | 说明 |
|---|---|---|---|
| `match_id` | string | 是 | 稳定 ID |
| `event_id` / `phase_id` | string | 是/否 | 所属赛事/阶段 |

### 3.7 Game（对阵内单局）

## 4. 校验规则（生成器必须执行，违反即构建失败）

1. `publish_status` 与 `progress_status` 独立；不存在合并枚举。
2. `publish_status=concept` → `schedule_status=tbd`、日期为空、页面不得出现「报名中」。
3. 每个公开数字必须有 `source_ref_id`；`verification_status=unverified` 的数字只能以「待核实」展示。
4. 未确认值只进 `*_candidate` / `*_status=pending` 字段，不写入展示字段。
5. RosterEntry 必须带 `event_id`；历史名单只追加 `snapshot_version`，不覆盖。
6. 队名/昵称变更只追加历史，不覆盖。
7. 历史赏金赛与未来赏金赛 `ruleset_id` 必须不同；S1/S2 导入记录必须 `category=historical_export` 或等价标记、`season_label=null`，不得生成正式赛季。
8. `format=bo3/bo5` 时 `games` 数量与结果必须自洽；未打完的 BO 标 `result.status=pending`。
9. 单场数据不得直接生成长期实力评分字段；评分字段在评分备忘录获准前不存在于公开数据。
10. 人物合并必须带 `confirmed_by/confirmed_at/evidence_ref_id`，未确认不合并。
11. `schedule_status=confirmed` 必须有来源；否则只能 tbd。
12. 数据文件带 `schema_version`；结构不符或引用缺失时构建失败并报错。

## 6. 待 Codex 审的点

1. 状态枚举是否够用；`announced` 与 `archived` 的迁移规则。
2. `Match`/`Game` 拆分是否满足 BO 多局与单局战报。
3. 拍卖式组队用 `team_formation=auction` + roster 快照是否够；是否需要记录队长资格来源。
4. 历史名单快照版本的最小可用方案（当前只有 `roster_id` + `snapshot_version`）。
5. 单场数据 → 长期评分的边界是否需要单独字段（建议：评分数据放独立 `ratings` 命名空间，默认不生成）。
6. 公告草稿与已发布是否用独立集合（当前用 `publish_status`）。
