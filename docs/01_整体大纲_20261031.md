## 5. 选手体系（重点：S1 人多、后续还会加）

### 5.1 数据现状与增长

- S1：37 条位置记录 → **32 个唯一昵称**（5 人在 2 个位置出现，按「同昵称+同队伍」合并为一人，页面里列出多位置）。
- S2：10 人，与 S1 **无重叠**（目前）。
- 后续：更多比赛、更多选手、同一选手多场/多赛事 → 页面数会从 42 增长到几十上百。

### 5.2 原则

1. **一人一页，自动生成**：页面由数据 JSON 渲染，不手写；新增选手 = 加数据 + 重跑生成脚本。
2. **稳定 ID + 可读 URL**：`player_id`（如 `s1-<slug>`）+ slug（昵称转写/拼音/短哈希），昵称改了 URL 尽量不变。
3. **合并规则先保守**：同昵称+同队伍 → 合并；跨赛事同昵称 → 先分开、等 Jason 确认后再合并（不猜）。
4. **数据完备度分级**：L0 仅昵称/队伍；L1 有 S1 六维；L2 有单场结算；L3 有多局/时间线/视频。页面上明确标「数据待补」，不空着装完整。
5. **来源标注**：每个数字带「赛事 + 场次 + 表/面板 + 日期」角标，点开来源说明。
6. **只发稳定标签**：不稳定标签不展示，写「数据不足/趋势未定」。
7. **认领与自填**：选手从选手页找到自己 → 「这是我的页面」→ 本地原型填自述/名场面 → 导出 JSON 审核；后端阶段再做登录。
8. **隐私**：只公开游戏昵称与游戏数据；不公开真实姓名/学校；选手可要求隐藏/删除。

### 5.3 页面骨架（每个选手页相同）

```
昵称 · 队伍 · 位置 · 代表英雄
数据条：KDA / 参团 / 胜率 / 场次（每项 ⓘ 来源）
稳定标签（不够稳定就写「数据不足」）
数据印象（一句话，不评价实力）
高光时间线（只列可归因事件；没有写「待补」）
视频区（有则嵌，无则占位）
选手自述（审核后显示）
分享按钮 + 来源脚注
```

## 6. 数据与技术方案

- **单一数据源**：`players_combined.json`（+ 补充的赛事/视频/内容 JSON）→ Python 生成器 → 静态自包含 HTML。新增数据只改 JSON，不改页面。
- **本地预览优先**：生成后双击 `index.html` 即可看，断网可看；本轮先做这个。
- **GitHub**：代码与页面放 Jason 的 GitHub（`github.com/ShengJunqi`），仓库名建议 `zongshi-cup-site`；先 private，确认后再考虑公开 + GitHub Pages 在线预览。
- **无后端 v1**：自填/投票走 localStorage 原型；登录、审核、防刷、内容管理放 v1.2（需要部署与账号）。
- **不引入框架**：原生 HTML/CSS/JS，控制体积与加载速度；英雄图标等游戏素材后续再定版权口径。

## 12. 红线与验收

**红线**：不编战绩/胜率/奖金/日期；未确认写「待公布/待核实」；只公开游戏昵称与游戏数据；未校准模型不叫「预测胜率」；国服数据不混国际服；不拿选手开恶意玩笑，输的一方留体面。

**验收**：手机打开不崩、加载不慢；每个选手找得到自己；数据点回来源；无编造；自填流程能走通（本地原型也算）。
