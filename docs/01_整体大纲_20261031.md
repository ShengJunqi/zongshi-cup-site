## 3. 赛事结构（三类方向，细节待讨论）

| 赛事方向 | 当前理解 | 网站需要支持 | 尚待决定 |
|---|---|---|---|
| 长周期正式赛事 | 可能包含季前阶段、常规赛、季后赛 | 阶段说明、赛程、队伍、积分/晋级情况、公告 | 阶段是否全部设置、队伍与赛制、时间安排 |
| 赛季中赏金赛 | 部分表现好的选手带队，类似拍卖选人，一天内完成单败淘汰 | 独立规则页、组队结果、对阵图、比赛结果 | 队长资格、选人方式、预算单位、队伍数、BO 几 |
| 小型排位赛 | 随机或平衡组队，持续参加形成个人记录 | 场次记录、参赛入口、个人历史、评分说明 | 匹配方式、计分方式、异常与争议处理 |

**数据建模要求**：赛事类型、阶段、组队方式、淘汰方式分别记录。例如「赏金赛」是活动类别，「单败」是赛制，「拍卖」是组队方式——代码与数据里不能绑成一个不可改变的固定模式。

## 4. 网站本轮改动

### 4.1 导航

手机主导航：**首页 / 赛事 / 赛程 / 选手**。
战报从「赛程」中的已结束比赛进入；视频、数据、模型放二级入口。

### 4.2 首页优先呈现

1. 最新公告与近期赛事；
2. 下一场比赛或待公布状态；
3. 近期赛果与战报；
4. 选手入口与精选内容。

**状态展示纪律**：没有确认日期 → 直接显示「赛程待公布」，不放示范日期或假倒计时；构想中的比赛不得显示「报名中」。

### 4.3 本轮 M1 样板（保留原样板 + 必要入口）

- 首页；
- 一个赛事详情页（公告、规则状态、简版赛程）；
- 一篇真实单场战报；
- 一个样板选手页；
- 来源页。

若用未来赛事演示：明确标「筹备方案，尚未公布」，与真实历史赛事分开。
继续提交 **320 / 390 / 430 三档手机截图** 和 **一张 1080×1440 分享卡**；**本轮不批量生成全部选手页**。

### 4.4 A 风格执行要求

- 执行基线：`mockups/style_a.html`（夜战金）；
- 优先修可读性：正文 ≥14px（尽量 15–16px）、辅助信息 ≥12px、对比度、行高、点击区 ≥44px；
- 表格与正文减少金色泛用，金色只强调主操作与关键结果；
- 手机优先，三档宽度都不得横向溢出；
- 分享卡单独设计，不截长网页。

## 5. 评分系统：先定用途，再谈公式

三个问题必须分开，不得混成一个总分：

| 系统 | 回答的问题 |
|---|---|
| 赛事积分 | 队伍怎样排名、怎样晋级？ |
| 个人竞技评分 | 如何估计水平、帮助组队匹配？ |
| 单场表现评价 | 这一场有哪些表现和贡献？ |

- 不得把 KDA、胜率、参赛次数、人气投票直接混成一个总分。
- 本轮 DeepSeek 只提交**评分设计备忘录**（用途、数据缺口、局限、位置差异、防刷、新人/退赛/争议、版本记录），不写公式。
- 现状：S1 每人约 1–2 场、S2 主要一场数据，**不足以支持可信的长期实力榜**。
- 现阶段：可展示真实比赛记录；评分只内部试算，不据此决定队长资格，不公开给选手定级。
- 评分能否由现有王者建模项目支持（数据、指标、样本门槛）需向建模会话确认，**不能默认已具备**；需求见 `docs/07_外部对接需求清单_20261031.md` M4。

详见 `docs/05_评分设计备忘录_20261031.md`。

## 7. 参赛者反馈收集

- 先找约 **5–8 名**不同经历参赛者（队长、普通队员、不同位置、可能首次参赛），不马上做大问卷。
- 第一轮看需求：可参赛时间、能接受多长赛季、固定队还是临时队、对拍卖组队的顾虑、个人评分用在哪里。
- 第二轮看样板：能否找到下一场比赛、看懂赛事状态、找到自己的档案、理解数据来源。
- 不问「网站好不好看」；给具体任务：「找到下一场比赛的时间和规则」，记录卡在哪。
- DeepSeek 准备提纲与记录表；Jason/协作者负责邀请与沟通。
- 意见按「多人共同需求 / 个别偏好 / 公平性问题 / 待验证建议」整理；**不因一条建议直接加功能**。

详见 `docs/06_参赛者访谈提纲与记录表_20261031.md`。

## 8. 数据与契约

- 最小数据契约见 `docs/04_数据契约_v0.1_20261031.md`；先经 Codex 审，再进入样板。
- 必须区分「方案是否获准发布」与「赛事进行到哪」——**两个独立维度，不共用一个状态字段**。
- 必须区分：赛事类型（活动类别）/ 阶段 / 组队方式 / 淘汰方式 / 规则版本。
- 历史赏金赛与未来赏金赛使用不同 `ruleset_id`；S1/S2 属历史数据来源，**不自动等同于正式赛季**。
- 队伍名单必须关联具体赛事或阶段；新队伍不得覆盖历史名单。
- 每个公开数字保留来源与确认状态（见 `docs/02_事实与来源清单_20261031.md`）。
- 外部接口（视频制作 / 王者建模 / 事实侧）的需求单见 `docs/07_外部对接需求清单_20261031.md`；网站默认只读它们已批准的产物，不改其代码、原始数据和任务计划。

### 8.5 AI 理解王者（网站能力接入，不是新增研究任务）

| 阶段 | 做什么 | 不做什么 |
|---|---|---|
| 现在 | 展示已核实事实 + 审核过的分析，让战报能解释关键事件及影响 | 不用未经验证的解释补空 |
| 后续 | 接入建模会话成熟的局势分析/预测结果，标模型版本、适用边界、置信度、校准状态 | 不展示未校准胜率，不把模型输出写成事实 |
| 暂不做 | — | 站内自由问答 AI 助手、实时自动解说、未经验证的胜率展示 |

- 接入顺序：先事实与已审核分析（M1），再局势分析（建模会话输出可用后），最后才谈预测类展示。
- 评分先作为网站需求提出；是否由现有模型支持，向建模会话确认（`docs/07` M4）。

## 9. 公开范围

- Jason 已原则同意公开，不再重复询问 private/public。
- **网站公开、源码公开、选手资料公开是三个不同范围。**
- 执行端先检查当前文件及 Git 历史：凭据、未获许可资料、原始个人信息；再选择适合公开的代码与产物。
- 不为在线预览未经检查公开整个历史仓库；检查通过后推进公开预览；有阻碍时列明文件与处理方案。
- 是否能在当前账户直接部署由执行端实测，不凭旧计划假定。

## 10. 审核与成本控制

- M0 PASS 不作废，但**不覆盖**本轮新增范围；只对受影响部分增量审核。
- 审核输出沿用 `PASS / CHANGES`；每个问题标证据、影响、关闭条件；区分**阻断项 / 应修项 / 可选优化**。
- 每个工作包只给 Codex 相关差异、契约和必要截图；DeepSeek 先自检再送审。
- 复审只看未关闭问题与本次变更；同一实质问题连续两轮未解决，报告原因与可选方案，不自动无限循环。
- 不重复生成三套完整视觉，不提前铺开几十张选手页。
- 审核记录对应 commit；改动后受影响范围重新审核。
