## 5. 选手体系（重点：S1 人多、后续还会加）

### 5.1 数据现状与增长

- S1：37 条位置记录 → **32 个唯一昵称**（5 个昵称在 2 个位置出现，作为合并候选，未人工确认；页面暂按昵称展示多位置）。
- S2：10 人；与 S1 按昵称无重叠（待身份确认）。
- 后续：更多比赛、更多选手、同一选手多场/多赛事 → 页面数会从 42（当前计数）增长到几十上百；身份确认前 42 不是最终名单。

### 5.2 原则

1. **一人一页，自动生成**：页面由数据 JSON 渲染，不手写；新增选手 = 加数据 + 重跑生成脚本。
2. **稳定人物 ID + 可读 URL**：`player_id` 不依赖昵称/赛事（如 `p_0001`）；赛事、队伍、昵称历史单独关联；slug 只用于 URL，改名保留旧 URL 跳转。
3. **合并先保守**：同昵称+同队伍只作为「合并候选」写入待确认表，人工确认后才合并；跨赛事同昵称同理；未确认不合并、不覆盖。
4. **字段能力标记（不是实力等级）**：有 S1 六维 / 有单场结算 / 有时间线 / 有视频；页面明确哪些字段缺、为什么缺，不空着装完整。
5. **来源标注**：每个数字带「赛事 + 场次 + 表/面板 + 日期」角标，点开来源说明。
6. **只发稳定标签**：不稳定标签不展示，写「数据不足/趋势未定」。
7. **认领与自填**：选手从选手页找到自己 → 「这是我的页面」→ 本地原型填自述/名场面 → 导出 JSON **人工审核**；「公开」开关只是意向，不能直接上线；后端阶段再做登录/归属校验。
8. **自填禁区**：自述/名场面/导出 JSON 禁止出现真实姓名、学校、联系方式、住址、照片；运营发现即退回。只公开游戏昵称与游戏数据；选手可要求隐藏/删除，需有实际接收入口。

### 5.3 页面骨架（每个选手页相同）

```
昵称 · 队伍 · 位置 · 代表英雄
数据条：KDA / 参团 / 胜率 / 场次（每项 ⓘ 来源）
稳定标签（不够稳定就写「数据不足」）
数据印象（一句话，不评价实力）
高光时间线（只列可归因事件；没有写「待补」）
视频区（有则嵌，无则占位）
选手自述（审核后显示）
分享按钮 + 来源脚注
```

## 6. 数据与技术方案

- **单一数据源**：`players_combined.json`（+ 补充的赛事/视频/内容 JSON）→ Python 生成器 → 静态自包含 HTML。新增数据只改 JSON，不改页面。
- **本地预览优先**：生成后双击 `index.html` 即可看，断网可看；本轮先做这个。
- **GitHub**：已建 private 仓库 **https://github.com/ShengJunqi/zongshi-cup-site**（2026-10-31，M0 草稿已推送）；本地仓库 `D:\宗师杯视频\website`。上线预览时再决定是否转 public + GitHub Pages。
- **无后端 v1**：自填/投票走 localStorage 原型；登录、审核、防刷、内容管理放 v1.2（需要部署与账号）。
- **不引入框架**：原生 HTML/CSS/JS，控制体积与加载速度；英雄图标等游戏素材后续再定版权口径。

## 10. Codex 审核机制（建议）

- **审核门**：G0 大纲/IA → G1 UI 方向 → G2 每批页面（结构+代码+移动端）→ G3 事实/文案 → G4 上线前终检。
- **阻断项（Codex 必须 CHANGES）**：红线违规（编造/未标注待核实）、身份或数据来源缺失、核心路径不可用、隐私越界。审美意见标「必须改 / 可选」，避免无限返工。
- **数据/schema 门（G2.5）**：新增/修改数据字段、来源或合并关系，先审字段契约与校验报告，再进页面实现。
- **复审规则**：PASS 后若改动数据、组件或文案，受影响范围重新审核；审核记录必须带提交 SHA、文件范围、截图/预览版本、验证结果与逐项问题关闭表。
- **Codex 输出格式**：`PASS` / `CHANGES`（编号问题 + 证据 + 修改建议 + 审美调整），写到 `reviews/`。
- **DP 动作**：按 CHANGES 修改 → 复跑 Codex → 直到 PASS；重大分歧交 Jason。
- **执行方式**：Codex CLI 已实测可用（0.166，ChatGPT 登录，模型 gpt-6.1-sol，read-only 沙箱），非交互命令示例：
  `codex exec -C <repo> --skip-git-repo-check -s read-only -i <截图> -o <review.md> "审阅 docs/01... 与 mockups/..."`。
  结果落盘（`reviews/`），不口头冒充；DSH 的 `subagent_codex` 工具不在本会话工具列表里，用 CLI 达到同样效果。
- **记录**：每个工作包一个 review 文件，保留「谁、审了什么、结论、改了什么」。

## 12. 红线与验收

**红线**：不编战绩/胜率/奖金/日期；未确认写「待公布/待核实」；只公开游戏昵称与游戏数据；未校准模型不叫「预测胜率」；国服数据不混国际服；不拿选手开恶意玩笑，输的一方留体面。

**验收**：手机打开不崩、加载不慢；每个选手找得到自己；数据点回来源；无编造；自填流程能走通（本地原型也算）。
